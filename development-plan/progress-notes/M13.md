### The four routes

All need `Authorization: Bearer <CONTROL_API_TOKEN>`; errors have the M11 shape.

**`POST /v1/guardian/check`** (no body; heartbeat `trigger:guardian`) → `200`
```json
{"status": "ok", "checked": 10, "problems": [{"post_id", "platform", "account_id", "creator", "kind", "detail", "post_url"}],
 "unverifiable": 0, "suspects": 0, "removed_by_owner": 0, "manual_removals_pending": 0,
 "errors": [], "mass_event": [], "emergency_stop": false, "strikes": 0}
```
`status` is `already_running` (all counts 0) when another pass holds the lock, which is what an n8n retry
after a timeout gets. `kind` is `removed_by_platform`, `claimed` or `blocked`. `problems` lists at most 50.

**`POST /v1/guardian/takedown`** body `{"from", "subject", "body_text", "received_at", "message_id"}` (no
heartbeat) → `200`
```json
{"takedown_id": "<uuid>", "status": "ignored|actioned|partial|open", "is_takedown": true, "duplicate": false,
 "matched": {"creators": ["Handle"], "posts": 1, "how": ["link to our tiktok post"]},
 "actions": [{"action": "block_creator", "creator", "platform", "newly_blocked", "clips_dropped", "pending_posts_cancelled"},
             {"action": "remove_post", "post_id", "platform", "account_id", "outcome": "removed|already_gone|manual|failed", "method", "post_url", "detail"}],
 "strike": true, "emergency_stop": false}
```
Every field is optional and unknown fields are ignored; a field that is not text is turned into text.
Without a `message_id` (or with one over 512 characters) the id is `sha256:<hash of from, subject, body>`.
`is_takedown` is `null` when the email could not be classified. `422` only for a body that is not a JSON
object, `413` over 256 KiB (the M11 request limit).

**`POST /v1/stats/collect`** (no body; heartbeat `trigger:stats`) → `200`
`{"status": "ok|already_running", "accounts": 3, "posts": 41, "skipped": 0, "rate_limited": false, "errors": []}`

**`GET /v1/reports/daily?format=telegram|json[&day=YYYY-MM-DD]`** (no heartbeat) → `200`
`format=telegram`: `{"text": "<HTML-safe text, at most 3,900 characters>"}`. `format=json` (default): the
object with `day, timezone, generated_at, env, accounts[], views, top_clips[], ypp, posts, spikes, clips,
discovery, guardian, spend[], issues[]`. Default day: the day that just ended in `reports.timezone`.

### Emergency stop rules, as implemented

1. **Strikes** (docs/12 §1 and §4): a strike is a `takedowns` row with `is_takedown`, status `actioned` or
   `partial` and `actions.strike = true`: one per creator per claims pass that found a problem on a
   published post, and one per actioned takedown email that hit at least one real published post. When
   strikes within `guardian.strike_window_d` (7 days, both ends counted) are `>= guardian.strike_limit`
   (2; a limit below 1 is read as 1) the stop is set. Checked after every claims pass and every actioned
   email.
2. **Account-level removal** (not in docs/12; added because the docs rule would otherwise block many
   innocent creators): when at least `guardian.mass_missing_min` (5) posts of one platform are gone in
   one pass and they are at least `guardian.mass_missing_ratio` (0.8) of the posts read on that platform,
   posting stops at once and no creator is blocked. This is what a banned account, or a broken platform
   answer, looks like.
3. Setting the stop: `control.emergency_stop = true` and `control.stop_reason` in one transaction with
   the row locked, one event `guardian.stop` (critical), one critical Telegram message. A stop that is
   already on is left as it is (its reason is kept, no second event, no second message).
4. **Never cleared by the guardian.** After the owner clears it (`/start`, `POST /v1/control/start`, or
   the CLI), only strikes newer than the last `guardian.stop` event count, so the old strikes do not
   switch it back on at the next check; it takes `strike_limit` new ones.
5. Not stop rules (docs/12 does not make them one): an authorisation failure pauses the account (M10) and
   alerts; error rates alert. The task brief named these as examples; docs/12 has only the strike rule.

### Claim detection: what it sees without the OAuth token

| Signal | With the API key (today) | With the owner's OAuth token |
|---|---|---|
| YouTube video removed (by YouTube or by a strike) | yes, for public videos | yes, also private videos |
| `uploadStatus = rejected` (+ reason), country blocks, privacy changed away from public | yes, for public videos | yes |
| Anything about a **private** YouTube video (all staging posts) | **no**: the public API does not list them. Counted as `unverifiable`; with `guardian.check_private_posts = true` they are read through Upload-Post instead | yes |
| Content ID claim that only monetises or tracks; a copyright strike as such; a claim in dispute | **no** | **no** through `videos.list` either (that needs YouTube Studio or the Content ID API); the email YouTube sends reaches the takedown inbox only if it is forwarded there |
| TikTok post removed | yes ("TikTok video not found" from Upload-Post) | same |
| Instagram post removed | only after two passes in a row, and only while another Instagram post reads fine (Instagram's answer is "may have been deleted or the token expired") | same |
| TikTok or Instagram muted audio, restricted reach, a warning on the account | **no** | **no** |
| Emails from platforms or creators | yes, through the takedown inbox (P7) | same |

The OAuth path starts working with no code change: `YouTubeClient.has_oauth()` is asked on every pass and
on every removal. With a token, `get_status` reads each video (private ones too) and `delete_video`
deletes it; if those calls fail (revoked token), the API key and the Upload-Post unpublish endpoint are
used instead. An API error or a rate limit never counts as "the video is gone".

### Removing posts

- YouTube: OAuth `videos.delete` when a token exists, else (or on failure) Upload-Post
  `POST /api/uploadposts/posts/unpublish`. A failed removal stays `remove_failed` and is tried again on
  every claims pass.
- TikTok and Instagram: `delete_post` raises `NotSupported` → `posts.status = remove_failed`, event
  `post.remove_failed`, and this critical message (plain text; WF07 escapes it), 12 posts per message:

```
ACTION NEEDED: delete 2 post(s) by hand
Why: takedown request from Big Streamer <big@streamer.test>
These posts are still public. The system cannot delete them (Upload-Post has no delete for TikTok and Instagram), so please delete each one by hand:
1. tiktok @6starsclipping: https://www.tiktok.com/@6starsclipping/video/7300000000000000001
   How: open the link in the TikTok app, signed in as @6starsclipping > tap the three dots (or the Share arrow) > Delete > confirm.
2. instagram @6starsclippy: https://www.instagram.com/reel/CxBig001/
   How: open the link in the Instagram app, signed in as @6starsclippy > tap the three dots at the top right > Delete > confirm.
Nothing else is needed: the creator is already blocked, and the guardian marks each post as removed once it is gone. Until then it stays in the daily report.
```
- The creator is stopped in the same step: tier `blocked` (`tiers.block`), `claims_count + 1` (once per
  incident), clips that are `rendering`, `gating`, `precheck_pending` or `approved` become `removed`,
  pending posts become `skipped`. Each claims pass repeats this for every blocked creator, which catches
  a post that was being uploaded at that moment. **This also applies to a creator blocked by hand**
  (`sixstars discovery set-tier ... blocked`): their published posts are taken down at the next check.
- A flagged post is read on every pass; when the platform says it is gone it becomes `removed` (no
  strike, no message). The daily report lists the ones still waiting, with links.

### Takedown intake: threat model and balance

The inbox is public, so the trust boundary is the request body. Controls:

- The email selects only by comparison with our own rows: links to posts we published (id per platform),
  links to or ids of videos we clipped, YouTube channel ids, and creator names (compared without case,
  `@`, spaces and punctuation; at least `guardian.handle_match_min_chars` characters; never our own
  account names). No id from an email is sent to a platform; no link is opened or resolved (short links
  such as `vm.tiktok.com` therefore match nothing); look-alike hosts match nothing.
- The model's answer is untrusted too: the links and names P7 returns go through the same matching.
- Size: body over `guardian.takedown_body_max_chars` (20,000) is cut for storage and for the model,
  links are still read from the whole body (at most 200); sender 320 and subject 300 characters; control
  characters removed; at most 20 names.
- Idempotent on `message_id` (unique index). A failure halfway leaves the row open and unclassified, so
  n8n's retry is processed from the start; every step is safe to repeat.
- Flood: more than `guardian.takedown_max_per_hour` (60) classified emails in an hour → further emails
  are stored `open` without an AI call and one warning is sent.
- Not a takedown → `ignored`, an event, no Telegram message (the report counts them); otherwise spam
  would reach the owner's phone.

**Balance.** docs/12 and prompt P7 say missing a real request is worse than a false alarm. So: P7 says
takedown **and** something of ours matches → acted on in full (block, remove all the creator's posts,
strike) with no further doubt. P7 says takedown and nothing matches → nothing is changed, status `open`,
critical message "needs you". Classification failed → nothing is changed, status `open`, critical
message. The cost of this balance: a forged email that names a creator we posted gets that creator
blocked and their posts removed, and two such emails stop posting until the owner sends `/start`. Nothing
else can be reached through an email.

### Health and failover

- Incidents (`health.incident` / `health.recovered` events, key in `entity_id`): one alert when a check
  starts failing, one when it is fine again, across scheduler restarts.
- Services: `guardian.expected_services`; a worker service is alive when any process of its queue is
  (worker heartbeat names contain host and pid). A service that never wrote a heartbeat is reported.
- Restart storm: counted from worker heartbeat names seen within the window beyond those alive now.
  **`scheduler` and `live-manager` restarts cannot be counted**: their heartbeat name is fixed and no
  `started_at` is written (docs/12 expects `info.started_at`; that is written in `jobs.py` and the service
  modules, outside this task).
- Failover: all four triggers, grace from `guardian.failover_grace_s` (hourly 4200, discovery 1500,
  guardian 2700, stats 14400). When a trigger is missing the scheduler runs the job in a background
  thread and stamps the heartbeat `{"source": "failover"}`; while that stamp is the latest heartbeat n8n
  counts as missing, so the hourly slot is scheduled once per slot (`schedule_hourly_slot` is idempotent)
  and the others every `guardian.failover_interval_s`. A call from n8n removes the stamp → one "is back"
  message. A trigger that never fired is measured from the scheduler's start.
- Stuck jobs (`guardian.stuck_job_s`, a job hanging on a live worker): back to `queued`, or `failed` when
  out of attempts. `jobs.requeue_stale` (dead worker) is unchanged.
- Clip expiry: approved clips older than `posting.max_clip_age_h` → `expired`, event `clip.expired`.
- Pruning: `events` and `candidates` older than `cleanup.*_days` (incident events are kept).
- Heartbeat ages are measured with the database clock (`health.db_now`), which stamps the heartbeats; a
  first test run failed by one second because the local clock and the database clock differ.
- A hand check: 28 single changes to the rules (limits, comparisons, host checks, escaping) were applied
  one at a time; 24 failed the unit tests at once, the other 4 got a test (`test_guardian_edge_rules.py`).
- Launch summary: one `info` message in the last `launch.summary_lead_s` before `launch.launch_at`.

### Ambiguities resolved (the reading that protects the accounts)

1. **Stop rules**: only what docs/12 says (strikes), plus the account-level rule above.
2. **Strike for an email**: only when it hit a real published post; blocking a creator we never posted
   is not a strike. Otherwise anyone could stop posting by naming two known creators.
3. **A problem post that still exists** (rejected, country block, privacy changed) is deleted too, not
   only the creator's other posts.
4. **Privacy changed away from public** counts as a problem (docs/12), also when the owner did it by hand.
5. **Blocked creators' approved clips** are dropped: the posting engine does not look at the creator's
   tier, so without this a blocked creator's waiting clips would still be posted.
6. **Failover for the guardian and stats triggers** (docs/12 names two triggers).
7. **Failover heartbeat**: docs/12 says the failover "writes the heartbeat". It does, marked, so that a
   fresh heartbeat written by ourselves is not mistaken for n8n.
8. **`received_at`** from the email is stored for the record only; windows use the server's time.
9. **No Telegram message for an ignored email**; one critical message for a takedown that matched
   nothing.
10. **Unexpected route errors** still alert as `warn` (M11), not `critical`.
11. **Instagram's ambiguous answer** needs two passes and a healthy token before it counts.
12. **Posts on private accounts** are not judged without the OAuth token (setting to change that).
13. **Report**: "slots used" is the number of distinct hourly slots with a real or dry-run post; "skips"
    is the number of `posting.slot_skipped` / `posting.slot_empty` events (one slot can have several, one
    per account). "Shorts views 90d" is the sum of `posts.views` of our YouTube posts published in the
    last 90 days. Followers and total views come from the latest snapshot before the end of the day,
    their change from the latest snapshot before its start. The task brief says `post_stats`; the schema
    has `account_stats` and the `views/likes/comments/shares` columns of `posts`, which is what is used.
