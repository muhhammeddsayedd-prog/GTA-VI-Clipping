### Public API for M08 (VOD lane) and M14 (live lane)

```python
from sixstars.spikes import (
    DetectedSpike, LiveSpikeDetector, ReplayScan, SpikeConfig,
    analyse_replay, scan_replay, persist_spike, from_settings, learn_bots,
)

@dataclass(slots=True)
class DetectedSpike:
    mode: Literal["live", "replay"]
    peak_t: float; first_t: float            # chat clock: seconds from video start (replay), unix seconds (live)
    score_z: float
    parts: dict[str, float]                  # msgs_z, uniq_z, react_z, clipreq_z, audio_z (clamped to [-3, 10])
    msgs: int; uniq: int; reaction_count: int; clip_requests: int
    tier: Literal["S", "A", "B"]
    window_start: float; window_end: float; spike_floor: float
    pad_start: float; pad_end: float
    chat_sample: list[dict[str, Any]]        # up to 40 x {"t_rel", "user", "text"}; t_rel is seconds from peak_t
    baseline_mean: dict[str, float] = {}     # extra: baseline mean of each feature at the peak
    absorbed: list[DetectedSpike] = []       # extra: lower spikes merged into this one (replay)

@dataclass(frozen=True, slots=True)
class ReplayScan:
    spikes: list[DetectedSpike]              # time order
    bot_names: frozenset[str]                # store in chat_files.bot_names
    baseline_rate: float                     # median messages per bucket; store in chat_files.baseline_rate
    counted_messages: int; buckets: int

scan_replay(messages, stream_start=0.0, *, config=None, bot_names=None, loudness=None, end_guard_s=0.0) -> list[DetectedSpike]
analyse_replay(messages, stream_start=0.0, *, config=None, bot_names=None, loudness=None, end_guard_s=0.0) -> ReplayScan

class LiveSpikeDetector:
    def __init__(self, platform, stream_start, *, config=None, bot_names=(), listen_start=None)
    def feed(self, msg: ChatMessage) -> None
    def feed_loudness(self, t: float, level_db: float) -> None
    def tick(self, now: float) -> list[DetectedSpike]      # call every spikes.live_step_s
    bot_names: frozenset[str]; bots_learned: bool; suppressed: list[DetectedSpike]

persist_spike(detected, *, creator_id, live_session_id=None, video_id=None) -> str   # spikes.id (uuid text)

SpikeConfig.from_settings(overrides=None) -> SpikeConfig      # also sixstars.spikes.from_settings
SpikeConfig.from_mapping(values) -> SpikeConfig
```

What the callers must know:

- **Replay** (`mode="replay"`): `messages` is `ReplayChat.messages`; `stream_start` stays 0. `bot_names=None` learns bots from the whole file. Results are in time order; sort by `score_z` for "best first". A replay S is returned and stored as S; treating it as A for routing is the VOD lane's job (docs/05 section 5).
- **Live** (`mode="live"`): `stream_start` is the unix time the stream started (warm-up rule and anchor of the 5-second grid). `listen_start` defaults to the earliest time seen, so the backlog YouTube sends on connect extends the baseline. The detector needs 12 baseline buckets of its own listening time (150 s) before it can report anything. Messages are placed by their `t`, never by arrival.
- **YouTube live delivers batches up to 5 s late.** Tick with `now = time.time() - 5` (the poll interval) so each bucket is complete when it is scored. A late or missed tick is caught up (up to 120 steps).
- With `config=None` the live detector re-reads the settings on every tick (30-second cache), so a threshold change reaches a running detector.
- `tick` returns a spike as soon as its first bucket below `end_z` is complete (about 10 to 20 s after the peak on a short burst), or when the spike has lasted `max_len_s - lead_s`.
- **Audio**: feed `(t, dB)` loudness readings on the chat clock (`loudness=` in replay, `feed_loudness` live), for example one per second. The jump is the mean of the bucket minus the mean of the 30 s before it. Without readings `audio_z` is 0.
- `persist_spike` returns the existing id when the same spike (same mode, source and peak position) is already stored, writes nothing and emits no second event. Absorbed spikes are stored with status `merged` and `merged_into`.
- **Database row**: replay rows fill `spike_offset_s`, `window_start_s`, `window_end_s`; live rows fill `spike_wall`, `window_start_wall`, `window_end_wall` and leave the `_s` columns null (M14 knows the buffer offsets). `parts` holds the five z-scores plus `first_t`, `spike_floor`, `pad_start`, `pad_end` and `baseline_mean`, because the table has no columns for them.
- `learn_bots(messages)` (in `sixstars.spikes`) is the bot learner to use; see "Bugs found in sixstars.chat".

### Deviations from the milestone file

1. **One state machine for both modes.** A spike opens at the first candidate bucket, stays open while `score_z >= end_z`, and closes at the first bucket below `end_z`. "Consecutive candidate buckets form one spike" still holds; in addition a bucket between `end_z` and `z_b` does not split a spike. This is what makes live and replay agree and gives the window end directly.
2. **A spike cut at `max_len_s - lead_s` is reported once.** Nothing new opens until the score has fallen below `end_z`, in both modes.
3. **Merging.** Replay: peaks closer than `merge_gap_s` merge, the higher is kept (as specified). Live cannot take back an emitted spike, so a later spike inside the gap is dropped and kept in `detector.suppressed`. When the second of two close bursts is the higher one, replay keeps the second and live keeps the first.
4. **Live baseline.** On each step the newest `bucket_s` is scored against back-to-back (non-overlapping) buckets that end 30 s before it, built from the message buffer. So the baseline has the same statistics as in replay, and late YouTube batches still enter it.
5. **Live `first_t` can be up to `live_step_s` (5 s) earlier than in replay**, because the overlapping bucket that first sees the burst starts earlier. Peak and tier match (acceptance test 7).
6. **Tokens.** Runs of a repeated character are squeezed on both sides ("LMAOOOO" counts as "LMAO", "WWWW" as "W"), and a token written with a trailing `*` in the setting ("HAHA*") matches any word that starts with it. Multi-word tokens match runs of whole words, not raw substrings ("know wayne" is not "NO WAY").
7. **`chat_offset_s` moves only the window start**, exactly as the formula in the milestone says. The end is not shifted.
8. **Idempotent storage without a schema change**: an advisory transaction lock plus a lookup on (mode, source, position). The `spikes` table has no unique index for this and I did not add a migration.
9. **`end_guard_s`** (optional argument, default 0 = off) drops replay spikes in the last seconds of a chat. It exists because the real-data check showed goodbye messages spiking at the end of streams. There is no setting for it; see "Proposed settings".
10. **Fixture name**: the milestone names `tests/fixtures/chat_twitch_replay_small.json`; the real file from M03 is `tests/fixtures/chat/twitch_replay_sample.json`. It holds only the minutes around the burst, so everything before it is silence: the engine reports the burst as one S spike from 09:55:00 to 09:55:40 (the 51-message bucket at 09:55:10 is inside). `tests/fixtures/spikes/` was not needed.
11. **`tests/unit/test_smoke.py`**: removed `spikes scan` from the list of placeholder commands (the command is real now). This file is outside my listed scope; the change is one line.
12. **Test-first**: the modules and their tests were written together and run before each commit, but the first versions of the modules were written before their tests.
13. `PROGRESS.md` was not edited (orchestrator instruction); the real-VOD table is below.
14. `replay_scanned` is logged at debug level so the CLI table stays clean; `persist_spike` logs `spike_detected` at info with `spike_id`.

### Proposed settings (staging first; not applied anywhere, seeds untouched)

```sql
-- Thin YouTube chat never reaches 15 messages in 10 s.
update settings set value = '8'::jsonb where key = 'spikes.min_messages';
-- The first 15 minutes are greetings, technical problems and name polls.
update settings set value = '900'::jsonb where key = 'spikes.warmup_s';
-- Reactions must drive the score; message volume alone is mostly chat answering the streamer.
update settings set value = '{"msgs": 0.15, "uniq": 0.15, "react": 0.55, "clipreq": 0.1, "audio": 0.05}'::jsonb
  where key = 'spikes.weights';
-- Thresholds rescaled for the new weights (a saturated volume burst alone now scores 3.0).
update settings set value = '2.0'::jsonb where key = 'spikes.z_b';
update settings set value = '2.6'::jsonb where key = 'spikes.z_a';
update settings set value = '3.4'::jsonb where key = 'spikes.z_s';
```

`spikes.end_z` stays 1.5 (it must stay below `z_b`).

Not possible through settings today, for the orchestrator to decide:

- **End of stream.** With the tuned values 3 more spikes (2 YouTube, 1 Twitch) were goodbyes in the last 5 minutes of a stream. `scan_replay(..., end_guard_s=300)` removes them, but there is no setting key. Suggested: a new key `spikes.end_guard_s = 300` in a migration, passed by M08.
- **S tier on YouTube.** With the tuned values no YouTube spike reached S (best 2.96). If the express lane should fire on YouTube live, `z_s` needs its own look once live data exists.
- Tried and rejected: a longer reaction-token list (LO, OM, HAHA*, XD, KEKL, CAUGHT, EZ and 20 more) did not raise the reaction z-score of real moments, because it raises the baseline share as well.

### Observations about the algorithm (not changed, the spec is followed)

- **The reaction share is a weak signal on thin chat.** With 1 to 2 messages per bucket the baseline share jumps between 0, 0.5 and 1, so its standard deviation is about 0.3 and a bucket where 11 of 16 messages are laughter gets `react_z` of only 1.7. A count of reaction messages (or a minimum share as a candidate rule) would separate moments from noise much better than any weight. This needs a spec change.
- **A big spike raises the baseline deviation for the next 10 minutes**, so a second moment soon after it scores lower (seen in a synthetic test: 44 messages against a usual 8 scored 2.44 because a 158-message bucket was in the baseline). A median-based baseline would not have this.
- **Saturation**: on a quiet stream every strong burst has `msgs_z = uniq_z = 10`, so ranking between them depends on the reaction share only.

### Bugs and gaps found in `sixstars.chat` (not fixed there)

1. `filters.learn_bots` flags a viewer who posts the same short text 20 times (for example one emote), as M03 noted. Worked around in `sixstars.spikes.learn_bots`: the name rule ("...bot") is applied to all messages and the repeated-text rule only to texts of at least `BOT_PREFIX_CHARS` (20) characters. Callers should use the spikes version.
2. `twitch_replay.download` cannot crop (`-b`/`-e`), so a 12-hour VOD is always downloaded whole (84 s and 105 s for the two here). Not a bug.
3. Nothing else: the adapters and the JSON Lines helpers worked on all 7 YouTube and 5 Twitch chats downloaded. Three YouTube streams (`hbnt8mmL0ZI`, `wXp3DgiOAwQ`, `1SsL_prkl7k`) reported "no chat replay" (not checked by hand whether that is true for each).

`chat-downloader` is still in `pyproject.toml` and unused (M03 finding, unchanged).
