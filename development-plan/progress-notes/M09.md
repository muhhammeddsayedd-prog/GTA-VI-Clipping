### The cost model (why the YouTube route differs from docs/06)

The Apify actor costs $0.003 per video and the plan allows $19 a month, so it cannot run every 10 minutes. One pass now does:

| Step | Calls per pass | Cost |
|---|---|---|
| yt-dlp search: per term 1 live search + 1 recent search per sort (`relevance`, `views`), 40 results each | 12 processes for 4 terms (6 in parallel, about 3 s each) | free |
| Channel RSS of known creators (rotating slice) | 25 feeds | free |
| Data API `videos.list` (snippet, contentDetails, statistics, liveStreamingDetails) for every id found, 50 per call | about 8 calls | 8 quota units |
| Data API `channels.list` for creators without a follower count and for permission checks | 1 to 4 calls | 1 to 4 units |
| Apify | 0 (one small run every 6 hours, read by a later pass) | $0 in most passes |
| Claude P6 (Haiku) for creators about to be picked | up to 12 | about $0.0005 |

Measured on GTA 5: 12 units on a cold start, 9 on the next pass. Per day at 144 passes: **about 1,300 to 1,500 quota units (13 to 15 % of the 10,000 daily quota)**; the guard `discovery.youtube_quota_daily_units` is 3,000, and over it discovery scores from the search listing alone. `search.list` (100 units) is never used.

Apify: one run every `discovery.apify_interval_s` (6 h), alternating a live search and a recent-video search, `apify_max_results` 5 per term, `maxTotalChargeUsd` = terms x results x price. With 4 terms that is at most **$0.06 per run, $0.24 per day, $7.44 per 31-day month**; the one real run cost $0.048 (15 videos and one "NO_VIDEOS" row). Guards: `apify_daily_budget_usd` 0.40 and `apify_monthly_budget_usd` 12, both computed from every `apify` row in `api_usage`. A run is started in one pass and read in a later one (`discovery.apify_last_run` holds `{run_id, started_at, mode, collected, status, cost_usd}`); a pass never waits for Apify. In the real run Apify's 15 live results were the same kind of streams, and by eye largely the same streams, that yt-dlp had already found (the overlap was not counted), so Apify is a safety net (a second vantage point if YouTube starts blocking the server's searches), not a needed source. `discovery.apify_interval_s = 0` switches it off.

### Verified facts (source-driven)

- **yt-dlp 2026.10.26 has no `ytsearchdateN:` prefix any more** ("Unsupported url scheme"). Filtered searches go through a results URL with an `sp` parameter (extractor `youtube:search_url`). `ytsearch.build_sp` builds the value: `EgQQAUAB` = videos that are live now, `EgQIAxAB` = videos of this week, `CAMSBAgDEAE=` = the same sorted by views. These are the values the YouTube web filter menu sends; they are not a documented API. The live test checks them.
- A flat search row has `id`, `title`, `duration` (None while live), `concurrent_view_count` (live only), `live_status` (`is_live` / `was_live` / `is_upcoming` / None). **It has no upload time, likes, comments or subscriber count, and YouTube sometimes serves a listing variant without `channel`, `channel_id` and `view_count`** (seen in the committed fixture). So the listing alone is not enough to score a video: the Data API fills the gaps. Without the API key (or over the quota budget) rows without a channel id are dropped and videos have no views-per-hour.
- `videos.list` response fields were read from real responses (see the module docstring of `sources.py`). `liveStreamingDetails.concurrentViewers` is missing for some small live streams (hidden count); the listing's count is used then.
- YouTube pads a thin search with unrelated videos: a "GTA" live search returned "Rain Sounds For Sleeping" and a horror-game stream. `sources.on_topic` keeps a result only when title, tags or description name the game (search terms or `env.target_game`), or when it is at least in the Gaming category (role-play streams often name the game nowhere). A video found through a creator's RSS feed must name the game.
- One yt-dlp search takes about 3 s; 12 searches with 6 workers take about 8 s.

### How the score reflects chat activity (intake fact 6)

1. **Live `chat_rate` part (20 %)** is no longer the flat 0.5 when unknown. It uses the creator's measured rate (`chat_files.messages_count / duration_s` of chats we downloaded) or, without one, `viewers x discovery.chat_mpm_per_viewer` (0.01), through `min(1, log10(mpm + 1) / 3)`. A 200-viewer stream gets 0.16 on this part, a 20,000-viewer stream 0.77.
2. **A live stream with a hidden audience** scores 0 on viewers and chat (it scored exactly the cutoff before) and never gets a slot. `discovery.min_live_viewers` (50) is a hard floor for slots.
3. **Videos: the chat-replay bonus (5 points) is scaled** by the estimated number of chat messages against `discovery.chat_min_messages` (1,500, the M04 finding): measured rate x length, else the peak audience we saw while it was live x 0.01 x minutes, else `views x discovery.chat_msgs_per_view` (0.02).
4. **Videos: passive views count less.** If `(likes + 2 x comments) / views` is under `discovery.passive_views_engagement` (0.5 %), the views-per-hour part and the view-based chat estimate are multiplied by `ratio / 0.5 %`. Reason, from the first real pass: the top six videos were "Shorts feed" live streams with 1 to 7 million views, about 0.1 % likes and 0 to 5 comments; they scored 80+ on views per hour alone. With the rule they drop out of the top of the list, and the list above is what remains. Set the key to 0 to switch the rule off.

All four numbers are estimates set as settings, not measurements. Once the VOD lane has downloaded chats, `chat_files` gives real rates per creator and the estimates stop mattering for those creators.

### Creator tiers (decision D10)

- New creator: tier `auto`, `description_checked_at` null. Prompt P6 on the channel description gives `preferred` / `auto` / `restricted`; the verdict is cached on the row and read again after `discovery.permission_recheck_days` (14).
- **`discovery.require_permission_check` (true): a creator gets no live slot and no video job before the first check has run.** The pass checks the creators it is about to pick itself (live first, at most `permission_checks_per_run` = 12, in parallel); other new or stale creators get a `creator.permission` job (at most 25 per pass). If the check fails (budget, API error) the creator is simply not picked in this pass.
- `restricted` and `blocked` creators never produce a `candidates` row, a session or a job. When a creator becomes restricted or blocked, their waiting videos become `skipped` and the queued `vod.process` jobs are cancelled; their live session is released by the next pass (reason `creator_forbidden`).
- Exclusion mechanism: setting `discovery.excluded_channels` (channel ids or handles, optional `youtube:` / `twitch:` prefix) blocks a channel even before it is first seen; `sixstars discovery set-tier <platform> <channel> blocked --reason "..."` blocks a known creator. No exclusions were given, so the list is empty.
- `blocked` is never changed by a check. A tier set by hand (reason starts with "manual") survives a check unless the channel text forbids clipping.

### Deviations from the milestone file and docs/06

1. **YouTube sources**: yt-dlp search + Data API + RSS every pass, Apify every 6 hours (docs/06: Apify every pass). See the cost model.
2. **Extra scoring rules**: the four chat-activity points above. Unknown follower count gives 0.5 on size ratio (docs: floor of 1,000 followers, which would give every unknown channel the maximum).
3. **Growth**: compared with the observation closest to 30 minutes ago that is at least `min_observation_gap_s` old and at most 45 minutes old, so a stream known for 10 minutes already has a growth value (the acceptance test asks for this).
4. **`candidates` idempotency**: a source observed again within `discovery.min_observation_gap_s` (120 s) updates its newest row instead of adding one. Videos already in `videos` are not observed again (no API call, no row).
5. **Permission checks run inside the pass** as well as through jobs (point above), and unchecked creators wait.
6. **`discovery.max_vod_backlog` (24)**: no more videos are queued while that many wait with status `new`. Without it a low hourly queue (always the case before M06 to M10 run) would add 12 videos every 10 minutes for ever. Also `discovery.max_vod_per_creator_per_run` (1).
7. **One source per creator** compares handles without case, spaces and punctuation across platforms (there is no cross-platform identity in the schema).
8. **Lowering `live.max_slots` does not release running sessions**; it only stops new assignments. Sessions end through the cutoff rule.
9. **A missing Twitch category is "empty", not an error** (before release Twitch may have no "Grand Theft Auto VI" category).
10. **`tests/unit/test_smoke.py`**: the `discovery run-once` placeholder case was removed (the command is real now). This file is outside my listed paths; the test would fail otherwise.
11. `discovery.apify_last_run` holds an object, not a bare run id.
12. Permission lookups (`channels.list` for a check) are not stopped by the quota budget: they cost 1 unit per 50 creators and the tier matters more than the unit.
13. Constants that are not settings: formula constants of docs/06 (log scales, 0.08, 0.5 per claim, reach values), yt-dlp attempts (2) and socket timeout, Twitch game cache (24 h), Apify give-up time (1 h), the always-blocked title word "leak" (the milestone names it outside the setting).

### Open issues

- **Live cutoff and YouTube audiences.** With the docs' formula a steady stream scores 12.5 points less from its second observation on (growth 0 instead of the unknown 0.5). A steady YouTube stream needs roughly 9,000 viewers to stay at 55; GTA 5 on YouTube has one or two of those. Slots are still filled (a session is kept for 20 minutes after it drops and new streams arrive with 0.5), but they will rotate. If steadier slots are wanted before Twitch keys arrive, lower `discovery.live_score_cutoff` to about 45 (a setting; I did not change the seed).
- **Language is often wrong on YouTube.** Hindi streams with English titles and `defaultAudioLanguage: en` count as English. The transcript language (M06) would be the reliable signal; discovery could store it back on `creators.language`.
- **The Shorts-feed "GTA 5 LIVE" streams** still rank high while live (their concurrent viewers are real). If they are not wanted, add terms such as `#shortslive` to `discovery.title_blocklist`.
- **Twitch is untested against the real API** (no keys). It is covered against `FakeTwitchClient` only; `get_followers_total` with an app token stays unverified (M02 note).
- **Pass time on the server was not measured.** 39 to 46 s here, dominated by the tunnel. If it comes close to 60 s there, lower `discovery.permission_checks_per_run` first (each check is one Haiku call of several seconds).
- **`sp` filter values are undocumented** and can change; `tests/live/test_discovery_live.py` detects it. "Sort by upload date" (`date`) did not visibly sort by date in a trial, so the default sorts are `relevance` and `views`.
- **yt-dlp search from the Hetzner server**: reported to work at intake, not re-run from the server in this milestone. If YouTube blocks it there, set `PROXY_URL` (the wrapper passes it for platforms in `downloads.proxy_platforms`) or shorten `discovery.apify_interval_s`.
- The quota day is counted in UTC; Google resets at midnight Pacific time. With a 3,000-unit budget against 10,000 this does not matter.
- Migration 0006 must be pushed to both Supabase projects. Until then the code runs on `DEFAULTS`, except that `discovery.rss_cursor` and `discovery.twitch_game_cache` are created on first write.
- Module-level loggers (`_log = get_logger("discovery")`) bind `env` at import time, like `usage.py`; in a long-running process that is the right value.
