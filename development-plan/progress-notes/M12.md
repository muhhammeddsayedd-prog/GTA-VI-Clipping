## Deviations from the plan, and why

- **Retry wait is 5 s, not 10 s.** The n8n engine caps `waitBetweenTries` at 5000 ms. Nodes use
  `retryOnFail`, 3 tries, 5 s apart.
- **The notify secret is not stored in the workflow.** The `Config` node of WF07 holds its SHA-256 digest
  and the IF node hashes the incoming header. This keeps the required behaviour (200 and silence on a
  mismatch, which the webhook node's own header auth cannot do: it answers 403) without a plaintext secret
  in workflow JSON. Rotating the secret = run `apply` again.
- **WF07 has no separate Set node for the text**; the Telegram node builds it. It also HTML-escapes title
  and body (exception texts contain `<`) and cuts the body at 3500 characters (Telegram limit 4096).
- **WF04 has one extra node**, `Find processed label`: the Gmail node needs a label id, so the id of
  `6stars-processed` is looked up by name through the Gmail API with the same credential. The label must
  exist in the inbox before WF04 is activated; I did not create it (owner's mailbox).
- **WF08 replies** to `/stop` and `/start` with a fixed sentence built from `stopped`, because those routes
  return no `text`.
- Only WF09 and WF07 are active (the task brief overrides the milestone's "activate WF01, WF02 now").
- No node groups or sticky notes; workflows carry a description and node notes instead.

## Open issues for later milestones

- **WF01 timeout.** `docs/17` says `/v1/discovery/run` may take up to 60 s, the plan fixes the HTTP timeout
  at 30 s. A slow pass would time out and be retried (up to 3 overlapping passes) and then alert. Either
  the route answers within 30 s or the timeout of that one node should be raised.
- **WF02 retries** re-send `POST /v1/posting/hourly`; the route must stay idempotent per slot.
- **WF04** forwards every INBOX mail of the `Gmail account` credential to the API. A mail whose POST fails
  is not labelled and the Gmail trigger does not deliver it again; WF09 alerts with the execution link.
