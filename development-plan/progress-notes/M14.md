### How it works

**Recorder.** One run = `python -m streamlink --stdout --stream-types hls --http-timeout 20 --stream-timeout 30
--retry-open 2 --stream-sorting-excludes ">1080p60" [--twitch-disable-ads] [--http-proxy …]
[--http-cookies-file …] <url> best` piped (no shell) into `ffmpeg -i pipe:0 -map 0:v:0? -map 0:a:0? -c copy
-f segment -segment_time <live.segment_s> -segment_format mpegts -strftime 1 -flush_packets 1
<DATA_DIR>/live/<session>/seg_<run>_%Y%m%dT%H%M%S.ts`, with `TZ=UTC0` in the child environment so the names
are UTC on any machine. Twitch is recorded from `https://www.twitch.tv/<login>` (no API key). Timestamps are
**not** reset per segment: inside one run they continue, which is what makes a byte join of segments a
valid stream and lets the index use them.

**Index.** A segment's wall-clock time is the second in its name. For a cut, the first timestamp of each
segment within `live.anchor_span_s` of the window is read once with ffprobe; the run's anchor is the
smallest `name time − timestamp` (the least delayed delivery), and a segment starts at `anchor + timestamp`.
This removes the burst at the start of a run (the first 10 s of stream arrive in 5 s) and the 2 to 5 s
jitter of HLS delivery. A window never joins two runs (there is a hole between them): the run that holds
most of the window is used and the window is clamped to it.

**Cut.** The bytes of the covering segments, including the segment still being written, are fed to
`ffmpeg -f mpegts -i pipe:0 -t <length> -c copy <cuts>/<spike id>.mp4`. The file starts at a segment
boundary (a keyframe), so nothing is re-encoded and the start is exact; `Cut.file_start` tells the caller
where the file begins and the window is addressed in seconds inside it. Because the open segment is read
directly, nothing waits for a segment to close: the only wait is `live.cut_settle_s` (4 s) after the end
of the range, and for S tier the context after the window is limited to `live.express_pad_wait_s` (6 s
instead of the 15 s of `spikes.context_pad_s`).

**Session.** Chat thread: `chat.open_live` → `LiveSpikeDetector.feed`; `tick(now − 5 s)` on YouTube,
`now − 1 s` on Twitch, every `spikes.live_step_s`. Bot names are stored on the session once learned. A
closed spike gets its own thread: creator tier read fresh (restricted or blocked: dropped, no row, no
spend) → `persist_spike` → P1 with the chat sample only, budget lane `express` → `spike_confirm.apply` →
route → cut → `RenderInput` → job. A spike that is stored but no longer `detected` (a restarted detector
re-reading the YouTube backlog) is not handled twice.

**Stream start.** `live_sessions.started_at` and the detector's warm-up anchor are the start of the
*stream* as discovery recorded it (`candidates.started_at`), not the start of our recording; the replay
pass computes `offset = wall − started_at` and needs exactly that. When discovery has no start (or one
older than 48 h, a 24/7 stream) the first data of our recording is used. The stream title for P1 and P2
comes from the same `candidates` row.

**Reconnect policy.** A run that ends is classified (`blocked`, `throttled`, `ended`, `not_live`,
`network`, `error`, `stalled`, `start_timeout`). `blocked` is never retried by the session; `throttled`
(the stream arrives more than `live.max_lag_s` behind real time) is retried like the rest and counts
as a platform block when it outlasts the reconnects. Anything else is retried after
`live.reconnect_backoff_s`, up to `live.max_reconnects` failures in a row (a run that then records for
`live.reconnect_reset_s` clears the count; `live_sessions.reconnects` counts all of them). When the
retries are used up: a session that recorded anything becomes `ended` and its replay is scanned; one that
never recorded becomes `failed` (terminal; discovery queues the video itself later). A stream that ended
is therefore noticed 40 to 60 s after its last data with the seeded 3 reconnects.

**Manager.** Every `live.poll_s`: released rows → stop → `ended` + replay hand-off (or left `released`
when nothing was recorded); `recording` rows without a session (restart) → resumed, event `live.resumed`;
`assigned` rows by trend score while slots are free → started. A row becomes `recording` when the first
stream data arrives, not at the start attempt.

**Replay hand-off (D55).** YouTube: `vod_source_id` = the same video id, job `replay.scan`
`{"live_session_id"}` on `normal`, priority 25, `run_after` = now + `live.replay_delay_s`, dedupe
`replay:<session>`, status `replay_queued`. Twitch: job `replay.find` looks every
`live.replay_find_interval_s` (up to `live.replay_find_max_s`) for the archive whose `stream_id` is the
session's `source_id` (`TwitchClient.get_videos_by_user`), then queues the same `replay.scan`.

### How the blocked state behaves

1. A session start that streamlink (or the live chat) answers with the bot check, a 429 or a captcha is
   classified `blocked`; a stream that stays more than `live.max_lag_s` behind real time through
   `live.max_reconnects` restarts is treated the same way. The session is not retried: its row goes back to `released` (or `ended` when it
   had recorded) and the platform gets a back-off in `live.source_health`: 5 minutes after the first
   refusal, `live.blocked_backoff_s` (30 minutes) after every later one.
2. While a platform backs off, its assigned sessions are released without a start, so the slots are free
   for the other platform. No process is spawned, nothing is notified.
3. After `live.blocked_notify_after` (2) refusals in a row: one `warn` "Live source youtube is blocked"
   with the refusal text and the fix (`PROXY_URL` or `YOUTUBE_COOKIES_FILE`), event `live.source_blocked`.
   Then silence, however long it lasts: one start per 30 minutes probes the platform.
4. When a recording of that platform delivers data: one `info` "Live source youtube recovered", the state
   is cleared.
5. A new proxy or cookies file (containers restarted) ends the back-off at once.

Integration test `test_a_blocked_platform_is_backed_off_reported_once_and_recovers` walks this for 2.5
hours of simulated time: 6 starts, 1 warning, 1 recovery message, Twitch recording untouched. The
classification strings were read from streamlink 8.6.3's source; the real bot-check output was not seen
(it does not happen on this connection).

### Deviations from the milestone file and docs/07

1. **`-reset_timestamps 1` is not used** and segment names carry a run number. Continuous timestamps are
   what the index and the byte join rely on.
2. **`extract` does not wait for the closing segment** (docs/07: up to 70 s). It reads the open segment.
   `live.cut_wait_max_s` (70) only caps the wait for a window that ends in the future.
3. **The cut happens in the live manager, not in the `express.render` handler**, and the job is the
   factory's own `express.render` with a `RenderInput` payload (M06's contract). The worker needs no
   access to the session's state, and the buffer cannot be swept between the spike and the cut.
4. **The cut is an `.mp4` that starts at a segment boundary**, not a `.ts` trimmed with `-ss`: exact
   start, positions passed as seconds in the file.
5. **Threads, not asyncio**, for the manager; each session has one asyncio chat thread. The database
   layer is blocking.
6. **The quality limit is `--stream-sorting-excludes ">{live.max_height}p60"` with `best`** instead of a
   fixed list: `1080p60` sorts above `1080p` in streamlink, so `>1080p` silently recorded 720p (seen on
   Twitch in the first trial).
7. **`--stream-types hls`**: without it streamlink plays the finished video of an ended YouTube stream
   from its start (checked: a past stream returned a 360p progressive stream).
8. **`ended` versus `failed`**: see "Reconnect policy". docs/07 sends every exhausted retry to `failed`.
9. **`replay.find` exists for Twitch only**; YouTube queues `replay.scan` directly with a delay and does

### Found in the real checks and fixed

- **False stall.** The stall watch compared the bytes of the run on disk. Once the buffer is full the
  janitor deletes an old segment for every new one, the total stops growing, and both recorders were
  restarted as "stalled" 45 s later (first full run, 6.5 minutes in). It now looks at the newest segment
  only; regression test in `tests/unit/live/test_live_recorder.py`.
- **1080p60 excluded** (deviation 6) and **finished YouTube video recorded as live** (deviation 7).
- **Clock skew in the stage times.** `jobs.locked_at` is written by Postgres, the other times by the
  host; this desktop's clock is 4.2 s behind, which showed up as 5 s of "queue wait". The hook now moves
  the database time onto the host clock.
- **A refused start reported the wrong line** ("No playable streams" instead of the bot-check text);
  the notification now carries the refusal itself.
- **A stream served slower than real time** (the YouTube slow spell above) kept a recorder "healthy"
  with a buffer drifting away from the wall clock. `Recorder.poll` now reads the first timestamp of
  every closed segment and ends a run that is more than `live.max_lag_s` (30 s) behind as `throttled`
  (`delivery_lag`, pure). `sixstars live probe` prints `lag_s` and exits 3 for it.
- **Twitch ad breaks.** With `--twitch-disable-ads` streamlink writes nothing while ads run. The recorder
  reads streamlink's own "Filtering out segments and pausing stream output" / "Resuming stream output"
  lines and does not count that silence as a stall (up to `live.ad_break_max_s`). Tested with a fake run
  only: no ad break occurred in the recordings.

### Gaps and things for other packages (not changed)

- **`tests/unit/chat/conftest.py` skips every test under a directory named `live`.** Its hook tests
  `"live" in item.keywords`, meaning the marker, but pytest also lists the names of a test's directories
  among its keywords. In a whole-suite run the tests of `tests/unit/live/` were skipped silently
  ("network test: set RUN_LIVE_TESTS=1"). Worked around with `tests/unit/live/conftest.py`, which takes
  that skip mark off this directory's tests; the fix at the source is
  `item.get_closest_marker("live") is not None`.
- **Discovery re-assigns a blocked platform's streams every pass.** The live lane releases them again
  without a start (one `live.released` event each), so nothing loops or alerts, but the slots are not
  offered to the other platform in that pass. Discovery could read `live.source_health` and skip a
  platform whose `skip_until` is in the future.
- **`spikes.warmup_s` (900) now counts from the real stream start.** When discovery has no start for a
  stream, the first 15 minutes of our recording produce no spikes.
- **The live detector's lag is the main part of the latency before the render** (see the table): a spike
  is reported when the first bucket below `end_z` is complete, 28 to 44 s after the peak for a 16-second
  burst. An "early report at the peak, fix the end later" rule would cut 15 to 20 s; it is a change to
  `spikes/detector.py` (M04).
- **A window that overlaps a Twitch ad break** is cut from a stream with a hole; positions after the hole
  are shifted by the length of the break. Not handled.
- **The host clock must be right** (NTP). Chat times come from the platform, segment times from the
  host; this desktop is 4.2 s off, the containers on the server use the host clock.
- `docs/07-live-lane.md` still describes `chat-downloader`, `-reset_timestamps 1` and the 70 s wait; not
  edited (outside my files).

exists (the same two things the VOD lane waits for). Enabling it anyway is safe but pointless: the lane
would release every slot, send one warning and probe every 30 minutes.

### Recommendation

- **Staging: safe to enable** once step 1 records. `live.max_slots` **2** to start (the seed says 3;
  two slots leave CPU for the express render on 4 shared vCPU until its latency is measured there), with
  `live.segment_s` 20 (a cut then carries at most 20 s of lead-in instead of 60).
- **Production: `live.max_slots = 0` for launch.** The lane idles cleanly at 0 (integration test, and
  the service only heartbeats). It should be enabled after the staging acceptance run (A2 to A4), not
  before: no real spike, no server run and no two-hour run exist yet.
