Job types (both on the `express` queue, because posting jobs are short and the normal queue can be busy
with a long render):

| Type | Payload | Priority | Does |
|---|---|---|---|
| `post.hourly` | `{"slot_at": "<ISO hour>"}` | 50 | `run_hourly_slot`; dedupe key `post.hourly:<slot>` |
| `post.retry` | `{"kind": "publish", "post_id", "clip_id"}` | 90 spike, 60 hourly | resumes one post: reads its status, or sends it again with the same key; also fills a missing TikTok URL |
| `post.retry` | `{"kind": "spike", "clip_id"}` | 90 | `try_post_spike` again at the end of the minimum gap (R4) |

CLI (new group `posting`; the old placeholder `sixstars post hourly` was left untouched as instructed):

- `sixstars posting plan [--slot ISO]`: prints the decision per account for the slot. Writes nothing.
- `sixstars posting hourly [--dry-run]`: runs the current slot now without jitter (`--dry-run` = `plan`).
- `sixstars posting trigger`: what the hourly trigger does.
- `sixstars posting clip <clip_id> --account <id>`: staging only (`APP_ENV=staging`), one clip to one
  account through the gate, the cap and the gap. This is the command for the private M10/M15 test post.

### How the lock and the keys work

- **Lock.** Both lanes decide inside `DbStore.planning_lock()`: one transaction that first takes the
  advisory lock `pg_advisory_xact_lock(hashtextextended('sixstars.posting.plan', 0))`, then reads the clock,
  the settings, the accounts and the history, decides, and inserts its `posts` rows (and their events and
  jobs) before it commits. A second planner waits (at most 30 s, then it fails and posts nothing), so it
  always sees the first planner's rows. Uploads happen after the commit, outside the lock.
- **Real key.** `post:<clip_id>:<account_id>` is the unique `posts.idempotency_key`, the `Idempotency-Key`
  header and the `request_id`, on every attempt. After a timeout the status is read first; the upload is
  sent again only when Upload-Post does not know the request.
- **Dry-run key.** `dry:<clip_id>:<account_id>:<slot>` (or `...:spike`): never equal to a real key, so a
  dry-run row cannot block the real row. A real row cancelled before sending is renamed `void:<post id>`.

### Behaviour worth knowing

1. **Emergency stop**: the trigger queues nothing; a lane that runs anyway writes no row, no event, no job
   and demotes nothing. A row planned just before the stop is cancelled at send time (`skipped`).
2. **Dry mode** (`launch.dry_run`, or before `launch.launch_at`): `posts` rows with `dry_run = true,
   status = skipped`, event `post.dry_run` with the fields that would be sent. The publisher never sends on
   `would_post`, only on a `pending` real row, and it runs `check_gate` again before the first send.
3. **Post states**: `pending` → `published` | `failed` | `skipped` (cancelled before anything was sent).
   `failed` rows keep their key and count toward the cap (rules, part 1), so a failed clip is not tried on
   that account again.
4. **Retries**: a send with an unknown outcome (timeout, network error, 5xx) is retried by `post.retry`
   after 30 s, 2 min and 5 min (3 retries), then the post is `failed`. A 4xx rejection is not retried.
   HTTP 409 (key in use) means the upload is in flight: the status is polled.
5. **Status polling**: `wait_for_upload` for 30 s in the call, then `post.retry` every 30 s. A post with
   no final status 20 minutes after it was planned becomes `failed` (warn alert).
6. **Recovery**: with every planned post a `post.retry` job is queued 10 minutes ahead, in the same
   transaction. If the worker dies between planning and sending, that job sends or resolves the post;
   otherwise it finds a finished post and does nothing.
7. **Rate limit** (HTTP 429, or a platform result classified `rate_limited`): `on_rate_limit` →
   `platform_accounts.paused_until`, `pause_reason`, lower `cap_24h` (YouTube), event
   `account.rate_limited`, warn alert, post `failed`.
8. **Authorisation** (`AccountAuthError`, a result classified `auth`, or a platform that is `skipped`
   because it is not connected): account paused for 24 h, event `account.auth_failed` (critical), critical
   alert. After reconnecting, clear `paused_until` by hand.
9. **TikTok**: `post_url = null` is stored as `published` and read again every 5 minutes for 20 minutes;
   `fallback_to_inbox` is stored as `failed` (`tiktok_inbox`), because nothing is public.
10. **Clip status**: a clip becomes `posted` when it has at least one published post and no post is still
    pending (docs/11 §6.4). An account that skipped the slot (TikTok outside its hours, minimum gap) does
    not get that clip later. A spike clip waits for its deferred accounts before it is `posted`.
11. **Spike lane** decides all approved spike-lane clips in one call, best rank first (R5), whichever clip
    the call was made for. `spikes.spike_to_post_s` is set by the first published spike post.
12. Events: `post.planned`, `post.dry_run`, `post.published`, `post.failed`, `post.cancelled`,
    `post.retry_scheduled`, `post.status_pending`, `post.link_updated`, `posting.slot_skipped`,
    `posting.slot_empty`, `posting.spike_skipped`, `posting.spike_deferred`, `clip.posted`, `clip.demoted`,
    `account.rate_limited`, `account.auth_failed`. Alerts: rate limit (warn), authorisation and missing API
    key (critical), failed post (warn), two empty hourly slots in a row (warn). A published post sends no
    Telegram message (M10 does not ask for one; 72 a day would be noise).

### Deviations and ambiguities (the reading that posts less was chosen)

1. **Hourly lane uses a job, not a sleeping background task** (as the task for this part says).
2. **CLI group is `posting`**, not `post`; `post hourly` stays a placeholder.
3. **Migration 0005 updates `youtube_main` only when it still has the seeded 40 / 8**, so running the
   migration again never undoes a cap that the system lowered after a rate limit.
4. **Two indexes on `posts`** were added in 0005 (clip id, creation time).
5. **`APP_ENV` other than `production`** (`dev`, `test`) gets the staging rules.
6. **Posting settings are read straight from the table**, not through the 30 s cache of
   `sixstars.settings`, so an emergency stop is seen by the next decision and the next send.
7. **`failed` for a rate-limited or unauthorised post**: the clip is not retried on that account.
8. **A missing video file or unusable upload fields** (no creator handle, staging privacy) → `failed`
   without any upload. The publisher reads `clips.local_path` only; it does not download from Storage.
9. **Polling is split** between the call (30 s) and `post.retry` jobs, so a worker is not blocked for 10
   minutes per post. The numbers 30 s, 20 min, 10 min, 24 h and 5 min are named constants in
   `publisher.py` (docs/11 gives fixed numbers without settings keys).
10. **Compilations (R10)** still do not exist: an empty queue skips the slot.
11. **No R7 demotion in dry mode** for a clip that has a dry-run record; it stays in the spike lane.
12. **A spike clip whose posts all failed** stays in the spike lane (approved) until it expires; it is
    demoted to the hourly lane only when `try_post_spike` is called for it again.
13. **A slow upload and the recovery job.** If one upload takes longer than 10 minutes, the recovery job
    may send the same file a second time. It carries the same idempotency key, so Upload-Post answers with
    the first job (or HTTP 409, which is polled): no second post, only a second transfer.
14. `tests/unit/posting/posting_helpers.py` mirrors the seed and now says 28 / 4; the rule test for a cap
    of 40 sets 40 explicitly.

### Bugs and gaps found outside this task's files

- **Nothing registers the posting job handlers.** `services/worker.py` has `register()` but no caller;
  M11 must call `sixstars.posting.handlers.register()` at worker start, or `post.hourly` and `post.retry`
  jobs fail with "no handler".
- **`UploadPostClient` guard reads the 30 s settings cache** and does not know `launch.launch_at`. The
  publisher's own gate check covers both; the guard stays a last line of defence.
- **`FakeUploadPostClient.upload_video` does not run the posting guard**, so the guard is only exercised by
  the M02 client tests.
- **`jobs` has no way to recover a job whose worker died while `running`** (no lock timeout). The
  recovery job described above covers posts; a lost `post.hourly` job means a missed slot.
- `tests/integration/conftest.py` does not clean `posts`, `clips`, `spikes`, `creators`,
  `platform_accounts`; the posting tests truncate them themselves (`tests/integration/posting_support.py`).
