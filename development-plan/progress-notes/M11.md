### Routes

All routes except the health check need `Authorization: Bearer <CONTROL_API_TOKEN>`. A missing, malformed
or wrong token, and a server without a token (unset or empty), all answer the same `401`
`{"error","code":"unauthorized","request_id"}` with `WWW-Authenticate: Bearer`.

| Route | Auth | Answer |
|---|---|---|
| `GET /v1/health` | none | `200 {"ok":true,"env"}`; `503 {"ok":false,"env","error","code":"db_unreachable"}` when the database gives no answer within 3 s |
| `POST /v1/discovery/run` | token | `200` the summary of `sixstars.discovery.run_discovery()` as a JSON object (dataclass, pydantic model or dict passed through); `501` while that function does not exist; `409 discovery_running` while a pass runs; `504 discovery_timeout` after 60 s (the pass continues); heartbeat `trigger:discovery` |
| `POST /v1/posting/hourly` | token | `202 {"status","slot_at","fires_at","job_id"}`; `status` is `scheduled`, `already_scheduled` (`job_id` null) or `stopped` (`fires_at` and `job_id` null); heartbeat `trigger:hourly` |
| `POST /v1/guardian/check` | token | `501 {"error","code":"not_implemented","milestone":"M13","request_id"}`; heartbeat `trigger:guardian` |
| `POST /v1/guardian/takedown` | token | `501`, same body; no heartbeat |
| `POST /v1/stats/collect` | token | `501`, same body; heartbeat `trigger:stats` |
| `GET /v1/reports/daily` | token | `501`, same body |
| `GET /v1/status?format=json` (default) | token | `200` object with `env, generated_at, posting_mode, emergency_stop, stop_reason, dry_run, launch_at, live_sessions{active,max_slots,by_status}, approved_queue{spike,hourly,hourly_low_watermark}, posts{last_hour{account:n}, last_24h{account:n}, accounts[...]}, spend_today_usd{total,by_provider,ai_daily_budget}, jobs{queued,running,failed_last_24h}, heartbeats[{name,kind,last_seen,age_s,stale}]` |
| `GET /v1/status?format=telegram` | token | `200 {"text": "<HTML-safe text>"}` (Telegram HTML parse mode; every database value is escaped) |
| `POST /v1/control/stop` body `{"reason"}` (optional, at most 500 characters) | token | `200 {"stopped":true,"reason","changed"}` |
| `POST /v1/control/start` | token | `200 {"stopped":false,"changed"}` |
| `POST /v1/control/settings` body `{"key","value"}` | token | `200 {"key","value","previous","description","updated_at","changed"}`; `404 unknown_setting`; `422 type_mismatch`, `invalid_value` or `validation_error` |

Errors always have the shape `{"error": "<text>", "code": "<code>", "request_id": "<id>"}` (validation
errors add `details: [{"field","problem"}]` and never repeat the input). Every answer carries
`X-Request-ID` (the caller's value when it is 8–64 characters of `A-Za-z0-9_-`, otherwise a new one),
`X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. A body over 256 KiB answers `413`
before authentication. An unexpected exception answers a generic `500`, is logged with its traceback and
request id, and sends one `warn` notification per route per 30 minutes.

Behaviour worth knowing:

- **Posts in `/v1/status`** count real published posts (`dry_run = false`, `status = published`) by
  `published_at`. Dry runs, failures and pending posts are separate fields per account.
- **`posting_mode`** is `stopped`, `dry_run` (the switch is on, or `launch.launch_at` is in the future or
  unreadable) or `live`.
- **Heartbeats in `/v1/status`**: triggers are always listed; a service is listed when it was seen in the
  last 24 hours (worker names contain the host name and the process id, so old ones would pile up).
  `stale` applies to services only, with `guardian.heartbeat_stale_s`.
- **Stop and start** write the two settings in one transaction, an event on every call (`control.stop`
  critical, `control.start` warn, with old and new values) and a critical Telegram message only when the
  flag really changed.
- **Settings route**: the key must exist (it never creates a setting); the new value must have the JSON
  type of the stored one, with two exceptions for nullable settings: a stored `null` accepts any type,
  and a stored string may become `null`. Event `setting.changed` (old, new) on every call, an `info`
  notification when the value changed. The row is locked while it is checked and written.
- **Log lines**: method, path (no query string), status, duration, request id. No headers and no bodies,
  so the token cannot be logged. `/v1/health` is logged only when it fails (the container polls it every
  30 s).

### Worker

- **Registration.** `services.worker.register_all()` runs at the start of `worker.run()`. It goes
  through `worker.HANDLER_MODULES` in `src/sixstars/services/worker.py`: each entry is `"module"` (its
  function `register`) or `"module:function"`, and that function must call
  `worker.register(job_type, handler)` for each of its job types. **A package is registered by one line
  in that tuple; nothing else changes.** Listed today: `sixstars.posting.handlers`,
  `sixstars.factory.pipeline:register_handlers`, `sixstars.gate.gate:install`,
  `sixstars.vod:register_handlers`, `sixstars.discovery.tiers:register_handlers`, and `handlers` modules
  for `precheck`, `live`, `guardian`, `stats`. Only posting exists on this branch; the other four names
  were given by the coordinator and are untested here (they are called without arguments). An entry whose
  module or function does not exist is skipped. One that exists but fails to import or register is logged
  (`handlers_module_failed`), reported as a critical Telegram message, and the worker continues with the
  other packages.
- **Shutdown.** SIGTERM or SIGINT stops claiming. The current job gets `SHUTDOWN_GRACE_S = 45` seconds
  (compose `stop_grace_period` is 60). If it is still running then, the job is given back
  (`jobs.release`: `queued`, runnable now, the interrupted attempt not counted) and the process exits. The
  old handler can never complete or fail the job afterwards. Handlers must be safe to run twice.
- **Dead workers.** `jobs.requeue_stale(stale_after_s)` takes back a `running` job when it was claimed
  longer ago than the threshold and the worker in `locked_by` has no heartbeat newer than the threshold.
  The lost attempt stays counted: with attempts left the job is queued to run now, otherwise it is
  `failed`, so a job that kills its worker every time stops after `max_attempts`. The scheduler calls it
  every minute with **`guardian.heartbeat_stale_s`** (300 s, an existing setting: "a service is unhealthy
  if its heartbeat is older than this"). Each recovered job is an event `job.recovered`; one `warn`
  message per pass. `guardian.stuck_job_s` (7200 s, "running jobs older than this are reset") is a
  different rule, for a job that hangs on a live worker; it is left to M13.

### Scheduler and live manager

- `sixstars scheduler`: heartbeat `scheduler` (30 s), `notify.retry_unsent()` (60 s), stale-job recovery
  (60 s), ranking refresh (600 s). A task that fails is logged and tried again after its interval.
  M13 adds its tasks to `scheduler.tasks()`.
- **Ranking refresh** (`scheduler.refresh_ranking`): for every approved clip with a score,
  `rank_score = posting.ranking.rank_score(...)` with the age taken from `spike_wall` for a live clip
  that has one, otherwise from `approved_at`. A clip that has a `clip.demoted` event and is in the hourly
  lane keeps the R7 boost (×1.5), so the refresh does not undo a demotion. Clips without a score are not
  touched. **Clips are not marked `expired` here** (the planner already ignores clips older than
  `posting.max_clip_age_h`; M13 lists expiry among its scheduler tasks).
- `sixstars live-manager`: heartbeat `live-manager` every 30 s, nothing else, runs until SIGTERM.

### Deviations from `docs/17` and M11

1. **Error bodies** have a third field, `request_id`.
2. **`/v1/health` answers 503** when the database is down (docs/17 only shows the good answer).
3. **`POST /v1/posting/hourly`** also returns `status` and `job_id`; under the emergency stop it still
   answers 202 with `fires_at: null` (n8n must not see an error for a stop that was asked for).
4. **`POST /v1/control/stop`** and `start` also return `reason` and `changed`.
5. **`POST /v1/control/settings`** refuses unknown keys and type changes (docs/17 says only "updated
   row").
6. **Discovery** answers 409 when a pass is already running and 504 after 60 s.
7. **Placeholders write their trigger heartbeat** before they answer 501, so the heartbeat means "n8n is
   calling".
8. **`/docs`, `/redoc` and `/openapi.json` are off**: the health check is the only route without a token.
9. **Worker: a broken handlers module does not stop the worker** (see above). The other reading, exit and
   let compose restart it, would stop all background work for one broken package.
10. **Unexpected errors alert as `warn`, not `critical`**, so a route that fails on every 10-minute
    trigger sends one message per 30 minutes.

### Changes needed in files outside this task

- **None is required** in `docker/docker-compose.yml`, `docker/Caddyfile` or the workflows. The existing
  health check (`curl -fsS --max-time 5 http://127.0.0.1:8080/v1/health`) works as it is: `-f` fails on
  the 503.
- **`docs/13` (n8n), WF01**: the common HTTP timeout is 30 s, but a discovery pass may take 60 s. Set the
  WF01 node's timeout to 90 s, or n8n will retry while the first pass runs (it then gets 409).
- **`docs/13`, WF03 and WF05**: until M13 these get 501 on every tick, and WF09 turns each into a
  Telegram error. Activate them with M13, or accept the noise.
- **`docs/17`**: add the fields and status codes listed under "Deviations".
- **`PROGRESS.md`**: the M11 entry should point here.

### Not done, not verified

- **SIGTERM on Linux in a container** was not exercised. On this Windows machine a process cannot be
  sent a catchable SIGTERM, so shutdown was tested by setting the stop event (the code path the signal
  handler takes). `docker compose stop` behaviour should be watched once on staging.
- **Discovery through the route** ran only with a stand-in function: `sixstars.discovery.run_discovery`
  did not exist on this branch.
- **No rate limit on failed logins.** The token is long and random and Caddy is the only way in; a limit
  on 401s would be a Caddy or a later API change.
- **The scheduler failover** (`guardian.failover_grace_s`), clip expiry and cleanup are M13.
- **`/v1/status` speed** was measured only over an SSH tunnel (about 2 s for its 7 queries); on the
  server it should take milliseconds.
