### Public API

```python
from sixstars.gate.decision import decide
from sixstars.gate.models import (ClipFacts, FileFacts, CreatorFacts, RecentClip, VisualFindings,
                                  GateSettings, ProfileLimits, PrecheckState, GateDecision, Verdict,
                                  ReasonCode, CheckResult)

decide(clip: ClipFacts, creator: CreatorFacts, recent: Sequence[RecentClip], settings: GateSettings,
       visual: VisualFindings | None, precheck: PrecheckState, now: datetime) -> GateDecision
```

`decide` is pure: no database, no network, no clock. The same inputs give the same decision. It raises `ValueError` for a naive `now` or a `clip.profile` other than `hourly` / `express`.

- `ClipFacts(id, creator_id, profile, lane, source_platform, source_id, start_s, end_s, duration_s, score, music_ratio, spoiler, safety_flags, hook, title, caption, hashtags, topic, transcript_text, word_spans, created_at, file, music_frames=None, subtitle_drift_s=None, is_compilation=False)`. `profile` is `clips.gate_profile`; `duration_s` is the clip without the end card; `word_spans` are (start, end) of every subtitle word in clip time; `file` is a `FileFacts` or None.
- `FileFacts(width, height, has_video, has_audio, duration_s, size_bytes, longest_black_s, longest_freeze_s)`; None for a number means "not measured" and fails.
- `CreatorFacts(id, tier, clips_today=0, prior_clips=0)`.
- `RecentClip(id, creator_id, status, source_platform, source_id, start_s, end_s, topic, transcript_text, decided_at, created_at)`.
- `VisualFindings(other_watermark, platform_logos, menu_or_loading, pause_or_brb_screen, empty_facecam, readable_subtitles, notes="")`: the P5 verdict; None rejects.
- `PrecheckState`: `unavailable` (no OAuth token), `disabled`, `quota_used`, `available`, `passed`, `claimed`, `inconclusive`.
- `GateSettings`: build it with `gate.profiles.settings_from_values({<setting key>: <JSON value>})` or `gate.profiles.load()`.
- `GateDecision(verdict, profile, lane, codes, reasons, checks, precheck, demoted, express_codes, express_checks, fallback_codes, risk_reasons)`; `.approved`, `.reject_reason` (first code of a rejection), `.as_json()` (the `clips.gate_result` document). `codes` and `reasons` are parallel. `verdict` is `approve` (no codes), `hold` (codes exactly `("precheck_required",)`) or `reject`.

Reason codes (`ReasonCode`, the string is what `clips.reject_reason` and the events carry), in the order of the checks: `creator_forbidden`, `creator_daily_cap`, `creator_tier_express`, `too_short`, `too_long`, `length_unknown`, `music_unknown`, `music_over_limit`, `spoiler_blocked`, `spoiler_in_text`, `safety_flag`, `safety_unknown`, `reject_topic`, `visual_unverified`, `watermark`, `platform_logo`, `black_frames`, `frozen_video`, `menu_or_loading`, `pause_screen`, `empty_facecam`, `unreadable_subtitles`, `subtitle_sync`, `score_too_low`, `score_unknown`, `duplicate_topic`, `duplicate_transcript`, `duplicate_source_range`, `file_missing`, `file_resolution`, `file_no_audio`, `file_too_large`, `file_duration`, `precheck_claim`, `precheck_inconclusive`, `precheck_required` (hold), `music_strict`. `gate_error` is set only by the job layer when the gate itself kept failing.

Check names in `gate_result.checks`, in order: `creator`, `length`, `music`, `spoiler`, `spoiler_text`, `safety`, `reject_topics`, `watermark`, `visual`, `subtitle_sync`, `score`, `duplicate_topic`, `source_range`, `file`, `precheck`. Each is `{"ok", "value", "limit"?, "codes"?, "reasons"?}`. Besides the docs/10 keys (`profile`, `passed`, `checks`) the document has `verdict`, `lane`, `codes`, `reasons`, `precheck`, `risk`, `demoted`, `express` (the express evaluation of a demoted clip), `hourly_fallback` (the hourly failures of a rejected express clip), `decided_at` and `inputs` (file measurements and the P5 verdict).

```python
from sixstars.gate import gate
gate.run_gate(clip_id, *, deps: GateDeps | None = None) -> GateOutcome      # what the factory hook calls
gate.after_render(clip_id, job)            # the hook itself: run_gate, never raises, queues clip.gate on failure
gate.install()                             # set_after_render for clip.render and express.render + job handlers
gate.resolve_precheck(clip_id, state, *, deps=None) -> GateOutcome          # judge a held clip again
gate.run_pending(older_than_s=0.0, *, deps=None) -> list[GateOutcome]       # every clip still in gating
gate.configure(GateDeps(...))              # collaborators of the hook and the handlers (tests pass fakes)
GateDeps(ai_client=None, youtube=None, storage=None, upload_post=UploadPostClient, clock=utcnow,
         ffmpeg="ffmpeg", ffprobe="ffprobe", upload_to_storage=True, hand_off=True)
GateOutcome(clip_id, status, decision, skipped, storage_path, spike_run, handoff_error, precheck_job_id)
```

Job types: `clip.gate` `{"clip_id"}` (queue of the render job; retry of a gate that failed), `clip.precheck` `{"clip_id"}` (queue `normal`), `clip.precheck_result` `{"clip_id", "check"}` (queue `normal`, `run_after` = now + `precheck.wait_s`).

Events (entity `clip`, service `gate` or `precheck`): `clip.approved`, `clip.rejected`, `clip.precheck_pending`, `clip.precheck_uploaded`, `clip.precheck_result`, `clip.precheck_delete_failed`, `clip.upload_failed`, `gate.handoff_failed`. The data of the first three: `verdict`, `profile`, `lane`, `codes`, `reasons`, `demoted`, `express_codes`, `risk`, `precheck`.

CLI:

```
sixstars gate run <clip_id> [--no-post]       # judge one clip in gating; exit 0 approved or held, 1 rejected, 2 not judged
sixstars gate pending [--older-than S] [--no-post]
sixstars gate explain <clip_id>               # print the stored verdict and every check; writes nothing
sixstars gate check-file <video> [--duration S] [--p5]    # measure a file; --p5 asks the vision model (costs money)
```

### What happens to a clip

1. `run_gate` acts only on status `gating`. It measures the file, then asks: would the clip be rejected even if the picture were fine? If yes, P5 is not called (the document says `inputs.p5 = "skipped…"`). Otherwise four frames (10%, 35%, 60%, 85% of the clip part) go to P5: lane `express` for the express profile, `vod` (daily budget) otherwise.
2. Inside one transaction that holds an advisory lock (`sixstars.gate.decide`), the creator, the other clips and the pre-check state are loaded, `decide` is called and the verdict is stored. Two gates never decide at the same time, so the duplicate checks of the second see what the first stored.
3. `approve`: status `approved`, `approved_at`, `lane`, `gate_profile`, `rank_score` (ranking stub: the score; for a clip moved out of the spike lane `posting.precedence.demoted_rank(score)`, so it goes to the top of the hourly queue), event `clip.approved`, upload to Storage (`pipeline.upload_clip`; a failed upload is a `clip.upload_failed` event, the approval stays, because posting reads the local file). A clip with lane `spike` is handed to `posting.spike.try_post_spike(clip_id, client)`; if that raises, the clip stays approved, `gate.handoff_failed` is written and a `post.retry` job (`kind: spike`) is queued. Hourly clips stay in the queue for the hourly slot.
4. `reject`: status `rejected`, `reject_reason` = first code, event `clip.rejected` with every code and sentence. **No Telegram message** (docs/10 names none): the events are there for the daily report (M13). The spike row is left as `clipped`.
5. `hold`: status `precheck_pending`, `needs_precheck`, job `clip.precheck`.
6. P5 or the database failing is not a verdict. `run_gate` raises and the clip stays in `gating`. The hook catches it and queues `clip.gate` (after the budget reset when the daily AI budget stopped P5). After the last attempt of that job the clip is rejected with `gate_error`, with one `warn` notification "Quality gate failed": a clip nobody could judge is never posted.

`control.emergency_stop`: the gate keeps judging. docs/16 says the stop halts posting while discovery and rendering continue, and docs/10 does not mention it. The posting engine refuses to post under the stop (tested here: the clip is approved, `try_post_spike` answers `stopped`, no post row).

### The stricter music rule (decision D103) as implemented

docs/10 does not name the rule; it is defined here.

- A clip is **risky** exactly as in docs/10 section 3: first clip of an `auto` creator, music ratio above 0 (or unknown), a compilation, or the P2 flag `copyrighted_media`.
- The pre-check has a state: `unavailable` when `YouTubeClient.has_oauth()` is false, `disabled` when `precheck.enabled` or `gate.hourly.precheck_risky` is false, `quota_used` when `precheck.daily_max` uploads were made today, else `available`.
- `available`: a risky hourly clip that passes everything else is held and pre-checked.
- `unavailable`, `disabled`, `quota_used`: no error, no waiting. A risky hourly clip is **rejected with `music_strict` when its music ratio is above `gate.strict_max_music_ratio`** (seeded `0.0`; the effective limit is never above `gate.hourly.max_music_ratio`). So today the hourly profile allows no music at all, like the express profile.
- **A clip whose `music_ratio` is NULL is always rejected (`music_unknown`)**, in both profiles and in every pre-check state.
- `copyrighted_media` is one of the P2 safety flags, so such a clip is rejected by the safety check before the pre-check matters. Compilations do not exist yet (no column); `ClipFacts.is_compilation` is always false from the loader.
- When the refresh token is added to the environment, `has_oauth()` becomes true after the worker restarts, the state becomes `available` and risky clips go to the pre-check. No code or setting changes (tested with `FakeYouTubeClient(oauth=False)` then `oauth=True`).
- If the pre-check stops being possible between the gate and the upload (token removed, switched off, quota used, upload failing on every attempt), the clip is judged again with that state: the same stricter rule.

Pre-check outcomes (`evaluate_status`): gone, rejected for `claim` / `copyright` / `trademark` / `legal` or without a reason, blocked or limited in any country → `claimed` (`precheck_claim`, creator `claims_count + 1`). `processed` → `passed`. `uploaded` (still processing) → read again after `precheck.wait_s`, at most `precheck.max_status_checks` times, then `inconclusive`. A failed upload or a rejection for another reason (`duplicate`, `length`) → `inconclusive` (`precheck_inconclusive`, no claim counted). The private copy is deleted in every case; a failed delete is a `clip.precheck_delete_failed` event and does not change the verdict. When the result arrives **every rule is applied again** at that time (spoiler date, duplicates), from the stored measurements; P5 is not called twice.

### Proposed settings changes (not made; the orchestrator decides)

1. **Music detector noise: set `gate.music_min_run_frames` to `2`. Leave `gate.express.max_music_ratio` at `0` and `gate.strict_max_music_ratio` at `0`.**
   What the express limit of 0 protects against: a spike clip is public within minutes and nothing checks it for copyrighted music (no pre-check in that lane, and now none in the hourly lane either). Music is the main cause of claims and strikes, and a strike on a new account costs more than a lost clip. That argument is about music that lasts long enough to be matched, not about one second.
   What the detector does on real footage (M06): in three of six runs one isolated second of speech over a game sound was flagged (Speech 0.77, Music 0.65), ratio 0.03 to 0.05. With every frame counted, about half of the otherwise good clips are rejected in both lanes today. Raising the ratio limit would be the wrong tool: a ratio of 0.05 is one second in a 20-second clip but more than two seconds of continuous music in a 45-second clip, and it would also let through several separate seconds.
   The setting ignores flagged seconds that stand alone (a run shorter than N seconds) and counts all others in full. It is the rule the factory already uses for ducking (`MIN_DUCK_FRAMES = 2`). With `2`, a single stray second passes and two seconds in a row still fail at ratio 0. The per-second flags come from the `clip.rendered` event; without them the stored ratio counts in full. Implemented and tested, off by default.
   Risk of accepting it: one real second of music (a sting, a car radio passing) gets through. I judge that small next to losing half the volume, but it is a weakening of the written rule, which is why it is not seeded.
2. **Spoiler terms are generic.** The seed has no character names or mission names. Before launch the owner should add GTA 6 terms once they are known (and for staging GTA 5: `deathwish`, `kill trevor`, `kill michael`). `dies` is not in the list on purpose: "he dies instantly" is an ordinary gameplay hook. Single words match whole words only (`ending` does not match `trending`), so `never-ending chase` is refused; that is accepted.
3. **Topic overlap for the same creator (`gate.duplicate.topic_overlap_same_creator` = 0.5) is strict.** P2 topics nearly all start with the same subject word (`streamer-…`, `player-…`), so two different moments of one creator such as `streamer-crashes-car-into-wall` and `streamer-crashes-bike-off-cliff` share half their words and the second is refused for 48 hours (6 hours for express). It is set this low because the two topics P2 wrote for one real moment (`new-player-robs-man-on-ground`, `player-caught-robbing-downed-player`) share exactly half. If the hourly queue runs short of clips from the most active creators, raise it to `0.75` and rely on the transcript and source-range checks for true repeats.
4. **`gate.checks.band_freeze_noise` (0.001) is calibrated on four real renders only.** See "P5 on real renders".

### Duplicate detection as implemented

- **Same source range** (docs/10): another clip of the same `source_platform` + `source_id` within `source_pad_s` (30 s, inclusive) of this clip's range, at any age. Rejected and still-rendering clips do not count. Of two clips of one moment that are both in the gate, the older one (by `created_at`, then id) wins, whichever is judged first.
- **Topic** inside the profile window (48 h hourly, 6 h express, inclusive; counted from the later of `approved_at` and `posted_at`), against clips that are `approved`, `posted`, `precheck_pending` or `removed`: an equal topic (case and separators ignored); or, for the same creator, shared words of at least `topic_overlap_same_creator` of the shorter topic (stemmed, at least two shared words); or, for any creator, a Jaccard overlap of at least `topic_overlap_any_creator`.
- **Transcript** (`duplicate_transcript`), same window and statuses, any creator: at least `transcript_overlap` of the shorter transcript's three-word sequences occur in the other. This is the check that catches the live clip and the replay clip of one moment (different `source_id`, same speech) whatever P2 called it. Unrelated speech shares almost no three-word sequences.

**Spend:** SPEND_PLACEHOLDER (limit $1).

**Black and freeze detection on the same files** (no API): all four real renders measure 0 s black and 0 s frozen with the final rules. The first version ran both detectors on a band of the gameplay only, with the docs/10 tolerance (`freezedetect n=0.003`), and reported `bub_normal` and `bub_express` as frozen for 2.5 s and 3.0 s: a car waiting at a traffic light at night. On the whole frame, which is what docs/10 describes, they are not frozen. But on the whole frame nothing is ever frozen or black in our renders, because the subtitles and the progress bar keep changing, so a frozen source would never be caught. Final rule: both detectors run on the whole frame with the docs/10 values **and** on the gameplay band (below the hook box, above the subtitle line, in both layouts) with tighter tolerances (`band_freeze_noise` 0.001, `band_black_pixel` 0.03), and the longer result counts. With those values the still night scene passes and a truly frozen or black source under moving overlays is caught (tested with ffmpeg-made files). This is calibrated on four files: a perfectly still two-second shot in real gameplay would still be rejected as frozen. If good clips are rejected with `frozen_video`, lower `band_freeze_noise`.

The detection adds one ffmpeg pass over the clip: 2.4 s for a 45-second and 1.7 s for a 28-second 1080x1920 file on this desktop, plus ffprobe and four frame grabs (the whole `check-file` command took 10 to 11 s including Python start-up and the database). Not measured on the server.

### Deviations from docs/10 and from the milestone file, ambiguities resolved (stricter reading)

1. **Pre-check not run on a real channel** (acceptance item "upload/check/delete cycle on the staging test channel"): impossible without the refresh token (D103). Built and tested against `FakeYouTubeClient`.
2. **Subtitle sync** (docs/10: subtitle word start minus transcript word start at most 0.3 s). The subtitles are drawn from the stored transcript, and nothing on the row holds a second timing, so the drift is zero by construction. The check verifies what can go wrong on the row: there are words, each lies inside the clip within 0.3 s, none ends before it starts. `ClipFacts.subtitle_drift_s` exists for a measured drift (a second transcription); the loader never fills it. M06 measured the real drift once by hand.
3. **A value that is missing fails**: no score, no music ratio, no safety object (or a flag that is not true or false), no spoiler flag while the block is active, no file, no P5 verdict, a detector that did not run, an unknown creator tier. docs/10 does not say; nothing is approved by default.
4. **Any P2 safety flag rejects**, including `hate` and `copyrighted_media`, and any flag name added later. "No slur as the focus" has no field of its own; it is the `hate` flag.
5. **`gate.reject_topics` is also a keyword check** on topic, hook, title, caption and hashtags (`reject_topic`), next to the P2 flags. The word `gambling` in a title rejects the clip even when P2 set no flag (an in-game casino clip titled "gambling" is refused).
6. **Spoiler terms are refused at any date** (D20: "never"), in hook, title, caption and hashtags. The transcript is not searched. The date rule: blocked while `now < gate.spoiler_block_until`; at exactly that time the clip is allowed.
7. **Auto-creator daily cap** counts the creator's other clips that were posted today (UTC) **or are approved or held and waiting**, so that no more than the cap can be posted in a day (the posting engine has no such cap). The cap is an hourly-profile rule, as in docs/10; the express profile has the tier rule instead.
8. **Express tier rule** is read from `gate.express.tiers` (`preferred`, `auto_no_music`, also `auto`). `auto_no_music` means a music ratio of exactly 0 after `gate.music_min_run_frames`.
9. **Express fallback**: "fails only express-specific checks but would pass the hourly profile" is implemented as: the express profile fails and the whole hourly profile passes. Then lane and profile become `hourly`. A demoted clip follows the hourly pre-check rules (held when risky and the pre-check can run). An express clip that fails the hourly profile too is rejected with the express failures as reasons; the hourly failures are in `gate_result.hourly_fallback`.
10. **Unreadable subtitles reject** (`unreadable_subtitles`). docs/10 lists only watermark, logos, menu, pause and facecam for P5; P5 also reports readability, and a clip with cut-off subtitles is a failed render.
11. **Limits are inclusive** where docs/10 gives a range or "≤" (length 20 to 60, music ≤ 0.10, drift ≤ 0.3, 100 MB of 10^6 bytes); black or frozen for "2 s or more" fails; a topic approved exactly 48 h ago still counts; a source range exactly 30 s away still counts.
12. **Pre-check disabled or over its daily maximum** is treated like "unavailable" (stricter music rule). docs/10 would approve those clips unchecked.
13. **File duration**: the file must be as long as `duration_s` + `factory.end_card_s` within `duration_tolerance_s` (1 s).
14. **`reject_reason` is a reason code**, not free text (docs/10: "the first failing check"). The sentences are in `gate_result.reasons` and in the event.
15. **Upload to Storage happens after the approval is stored**, and its failure does not undo the approval.
16. **`gate/music.py` holds no detector**: it is in `factory/music.py` (M06). No `clips` column was added.

### Bugs found elsewhere (not fixed)

- **P5 answers in the wrong shape on frames that have a problem.** On the two bad copies P5 was asked 7 times (13 API calls): the first reply was unusable in 6 of the 7, and the client's repair retry was unusable again in 3 of those 6. The two replies that were captured (one run) were `{"description": "...", "properties": {<the six fields and notes>}}`: the model filled in the outline of the JSON Schema that `clients/anthropic_client.system_with_schema` appends, instead of the object. The verdict inside `properties` was right both times. The other unusable replies were not captured; they are assumed to be the same. On the clean renders it did not happen (0 of 4). Effect today: `InvalidModelOutput`, the gate asks once more (`gate.visual.P5_ATTEMPTS = 2`), then the `clip.gate` job retries three times, then the clip is rejected with `gate_error` and a warning is sent. Nothing bad is approved, but bad clips cost up to 16 calls and end as "gate failed" instead of "watermark". Fix in `ai/` or the client: accept an object wrapped in `properties` when the top level has only `description` / `properties` / `type` / `title`, or say in the P5 prompt that the reply is the object itself. `invalid_model_output` still does not log why the reply was invalid (already noted in M05); a five-line script was needed to see it.
- **Nothing registers the factory, gate or posting handlers at worker start** (already noted by M06 and M10).
- `tests/integration/conftest.py` applies later migrations on every run with `on conflict do nothing`, so a settings row that a migration changed while it was being developed stays stale in an existing test database (hit here with `gate.checks`; the row had to be deleted by hand once).
- The integration suite is slow through the SSH tunnel: the M07 integration tests take about 9 s each, most of it database round trips of the shared fixtures.

### Open issues and what was not verified

- **Pre-check against the real YouTube API**: never run (no token). `upload_private`, `get_status`, `delete_video` are themselves unverified against Google (M02).
- **P5 on a real menu, loading, pause or empty-facecam clip**: not tested; only the watermark, logo and cut-off cases were made.
- **The crafted "music bed" clip of the acceptance list** was not run through the real PANNs detector here: the gate reads `clips.music_ratio`, and the detector was verified in M06. The music rules are tested from the stored ratio and flags.
- **Not run on the staging server or on Linux**; detection time measured on this desktop only.
- **Two gates at the same moment in two processes** is covered by the advisory lock but was not tested with real concurrent processes; the order-independence of the result is tested.
- **A private pre-check copy can be orphaned** if the upload succeeds and the database write that stores its id fails: the retry uploads a second copy and only that one is deleted.
- `gate_result` of a clip rejected without P5 shows the `watermark` and `visual` findings as not found; `inputs.p5` says that P5 was skipped.
- Rejected clips keep their local file; cleaning up is the retention job of M13 (docs/21).
