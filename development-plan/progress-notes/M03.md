### Public API for M04 and the lanes

```python
from sixstars import chat
from sixstars.chat import filters, synthetic
from sixstars.chat.models import ChatMessage, ReplayChat

chat.open_live(platform, channel, *, max_reconnects=None) -> AsyncGenerator[ChatMessage, None]
chat.download_replay(platform, source_id, *, raw_path=None) -> ReplayChat | None     # blocking

twitch_irc.stream(login, *, proxy=None, connector=None, max_reconnects=None, ...) -> AsyncGenerator[ChatMessage, None]
youtube_live.stream(video, *, proxy=None, cookies_file=None, include_backlog=True, max_reconnects=None, poll_max_s=5.0, ...) -> AsyncGenerator[ChatMessage, None]
twitch_replay.download(vod, out_path=None, *, cli_path=None, threads=8, proxy=None, timeout_s=900, attempts=3) -> ReplayChat
twitch_replay.parse_file(path, source_id=None) -> ReplayChat
youtube_replay.download(video, *, proxy=None, cookies_file=None, timeout_s=900, use_fallback=True) -> ReplayChat | None
await youtube_replay.fetch(video, *, proxy=None, cookies_file=None, timeout_s=900) -> ReplayChat | None

filters.FilterContext(warmup_s, ignore_users, stream_start=0.0, bot_names=frozenset())
filters.FilterContext.from_settings(stream_start=0.0, bot_names=()) -> FilterContext    # reads spikes.warmup_s, spikes.ignore_users
ctx.with_bots(names) -> FilterContext
filters.is_counted(msg, ctx) -> bool
filters.learn_bots(messages, *, min_messages=20, same_prefix_ratio=0.8, prefix_chars=20) -> set[str]
filters.cap_per_user(messages_in_bucket, max_per_user=3) -> list[ChatMessage]
```

Behaviour the callers must know:

- **Live `t` is unix seconds, replay `t` is seconds from the start of the video.** Twitch replay offsets are whole seconds.
- **Twitch live never ends by itself** (an offline channel is silent): the live lane stops it with `aclose()`. **YouTube live ends normally when the stream ends** and raises `ChatSourceError` when there is no live chat at all.
- **YouTube live sends a backlog first**: about 75 past messages with their true (older) timestamps. They are useful for the baseline; pass `include_backlog=False` to drop them. Messages then arrive in batches every 5 s at most, so arrival order is not strict time order across batches: bucket by `t`, not by arrival.
- **YouTube replay returns `None`** when the video has no chat replay (the VOD lane falls back to transcripts). `youtube_replay.VideoUnavailableError` (a `ChatSourceError`) means unplayable or still live. Right after a stream ends the replay may not exist yet: retry later before falling back.
- `max_reconnects=None` retries forever; a number raises `ChatConnectionError` after that many consecutive failed attempts.
- `username` is the display name (`@Handle` on YouTube). Bot lists hold `filters.normalise_name(...)` values (lowercase, no `@`); store `learn_bots` output directly in `bot_names`.
- `proxy_for` returns None without reading the database when `PROXY_URL` is unset; with it, it reads `downloads.proxy_platforms`.

### Verified facts and differences from the kit

1. **`chat-downloader` 0.2.8 is broken against YouTube, live and replay.** Every call fails with `chat_downloader.errors.ParsingError: Unable to parse initial video data`. Cause: it opens `https://www.youtube.com/live_chat?continuation=<token>` with the token from the watch page's view selector; YouTube now puts a short token there that is not valid on its own, and the page comes back with an empty `ytInitialData`. A newer User-Agent does not help, and neither does `chat_type="top"`. The package's last release is from 2023. **The adapters do not use it; the dependency can be removed from `pyproject.toml`** (not done: outside my scope).
2. **Working YouTube path**: watch page -> `conversationBar.liveChatRenderer.continuations[0]` -> `POST /youtubei/v1/live_chat/get_live_chat` (live) or `get_live_chat_replay` (finished). The first response lists the views "Top chat" and "Live chat"; the adapter switches to "Live chat" (all messages, the second entry). No API quota, no login.
3. **The watch page comes in two forms** (about 1 request in 9 got the new one): `var ytInitialData = {...};` and `<script id="yt-initial-data" type="application/json">`. The parser handles both; a parser that knows only the first will start failing when YouTube finishes that rollout.
4. **Kind mapping on YouTube**: text -> `chat`; paid message and paid sticker -> `donation`; membership item -> `sub`; gift purchase and gift redemption -> `gift` (the kit said "others -> notice"); engagement and mode-change messages -> `system`; unknown renderers -> `notice`. Ticker, banner and deletion actions are ignored.
5. **TwitchDownloaderCLI 1.56.5** (released 2026-07-20): `chatdownload -u/--id <vod> -o/--output <file>.json`. `--embed-images false` from `docs/08` is wrong today: `-E/--embed-images` is a switch that is off by default, so no flag is needed. Flags used: `--threads 8 --temp-path <dir> --collision Overwrite --banner false --log-level Error`. Without `--collision Overwrite` the CLI prompts when the file exists and would hang a job.
6. **TwitchDownloaderCLI JSON shape**: top level `FileInfo, streamer, clipper, video, comments, embeddedData`. `video` has `id, title, length, start, end, game, chapters`. A comment has `content_offset_seconds` (an integer), `commenter` (`_id, name, display_name`), `message` (`body, bits_spent, user_badges[]._id, fragments, emoticons`). **There is no `user_notice_params`** in today's output, so subs, gifts and raids cannot be told apart in a Twitch replay; they appear as ordinary comments or not at all. Only cheers (`bits_spent > 0`) are detected. The parser still honours `user_notice_params.msg-id` if a future version writes it.
7. **Twitch IRC**: works anonymously as documented. Extra `msg-id` values mapped to `gift`: `anonsubgift`, `anonsubmysterygift`. A cheer, a gift and a raid did not occur during the captures, so those unit tests use lines in the format of Twitch's documentation; `PRIVMSG`, `USERNOTICE resub`, `CLEARCHAT`, replies and `ACTION` lines are real captures.
8. **`youtube_live` does not use a thread or a queue** and `twitch_replay` uses 8 download threads, not the CLI default.

### Deviations from the milestone file

1. YouTube adapters use the web chat endpoint and yt-dlp instead of `chat-downloader` (fact 1).
2. Synthetic generators are in `src/sixstars/chat/synthetic.py`, not `tests/fixtures/synthetic_chat.py`, so M04's tests can import them (`tests/` has no packages).
3. Fixtures have at most 200 messages each (orchestrator brief), not ~2,000. The Twitch sample still contains a real burst: 51 messages in one 10 s bucket against a stream median of 7.
4. Network code for chat lives in `src/sixstars/chat/`, not in `src/sixstars/clients/` (the milestone places the adapters there; `clients/` belongs to M02). Each path has timeouts, retries with backoff and structured logs; tests use scripted fakes (`FakeConnection`, `httpx.MockTransport`, fake CLI runners).
5. Constants that are not settings, because `docs/16-settings-reference.md` has no keys for them: bot learning (20 messages, 80%, 20 characters), per-user cap (3), both passed as function parameters; reconnect backoff; IRC ping timings; YouTube poll interval (5 s); HTTP timeout (15 s); download timeout (900 s); TwitchDownloaderCLI threads (8).
6. Stream functions return `AsyncGenerator` (a subtype of the planned `AsyncIterator`) so callers can `aclose()`.
7. `PROGRESS.md` was not edited (orchestrator instruction); these notes replace the M03 entry.

### Open issues and things not verified

- **Nothing was run from a data-centre IP.** IP-sensitive points to test on the staging server: (a) EU servers can be sent to `consent.youtube.com`; the client sends the cookie `SOCS=CAI` to avoid it, and reports "redirected to the cookie consent page" if it still happens; (b) YouTube may answer a server IP with "Sign in to confirm you're not a bot" (`playabilityStatus`); the adapter still reads the chat when the page carries it, and otherwise raises `VideoUnavailableError` with that reason; (c) Twitch may rate-limit 8 parallel chat threads from one IP. `PROXY_URL` and `YOUTUBE_COOKIES_FILE` are accepted on every YouTube path.
- **Proxy paths are untested against a real proxy**: httpx `proxy=`, websockets `proxy=`, `yt-dlp --proxy`, and `HTTPS_PROXY`/`ALL_PROXY` for TwitchDownloaderCLI (it has no proxy flag; that .NET honours these variables for it was not checked).
- **A busy YouTube live chat was not observed** (the only large live GTA stream at test time had about 1 message per 10 s). The polling path is the same, but batch sizes under load are unverified.
- YouTube's "chat disabled" notice and "unplayable" pages are parsed from the known structure; no real example was captured.
- Twitch replays cannot mark subs, gifts and raids (fact 6): a sub train in a VOD cannot inflate counts through notices, but M04 should not rely on `kind` for Twitch replays.
- `learn_bots` flags a viewer who posts the same short text 20 times in the learning window (for example an emote), exactly as the doc's rule says. M04 may want to apply the repeated-text rule only to longer texts.
- Long, very busy replays are fetched sequentially on YouTube (about 45 messages per request, ~0.15 s each): a chat with 500,000 messages would take roughly half an hour, over the 900 s default timeout. Not seen in GTA RP streams tested; parallel fetching by offset is possible later.
- `docs/05`, `docs/07`, `docs/08` and `docs/14` still name `chat-downloader` and `--embed-images false`; not edited (outside my scope).
